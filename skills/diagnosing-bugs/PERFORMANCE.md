# Performance comparisons

1. Define the user-visible metric, representative inputs, and correctness check before changing code. Record the revision, runtime, dependencies, configuration, hardware or service limits, concurrency, and warm/cold cache state needed to repeat the measurement. Use the existing benchmark tools where possible.
2. Run the correctness check and repeated baseline measurements. Keep raw samples and state whether the metric is latency, tail latency, throughput, memory, or cost. A faster single request does not establish higher throughput or better tail latency. Use enough samples for the chosen metric; when the data cannot support it, report that limit.
3. Set a bounded experiment budget and the minimum useful improvement before trying variants. Change one causal hypothesis at a time. Reject a variant that fails correctness before comparing speed. Keep inputs and environment comparable; environmental changes invalidate the old baseline.
4. Compare repeated baseline and candidate runs, interleaving them when drift is plausible. Retest the apparent winner against the baseline on the original scenario. Report the sample spread and regressions as well as the chosen statistic. Overlapping noise is inconclusive, not a demonstrated improvement.
5. Stop when the budget is reached, the improvement is below the useful threshold, or the signal cannot be separated from noise. Retain the known-correct implementation unless the comparison justifies a change. Preserve failed variants and their evidence in the diagnosis report so another session does not repeat them.
